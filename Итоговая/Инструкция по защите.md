# Защита итоговой работы — что и как показывать

Главная мысль, которую нужно донести: **своего сервера больше нет**. Вся серверная часть — это база данных PostgreSQL в Supabase, описанная двумя SQL-скриптами (`Итоговая/supabase/schema.sql` и `seed.sql`). REST API по этой базе платформа строит сама (PostgREST), вход и регистрацию выполняет Supabase Auth. Права ролей и проверки данных выполняет сама база, поэтому их не обойти даже запросом мимо приложения.

Порядок показа рассчитан на 7–10 минут. Если времени мало, покажите шаги 2, 3, 4 и 5.

## 5. Роли и права — «права проверяет база» (2 минуты)

**В приложении:**
1. Меню пользователя (кружок с буквой справа вверху) → **Выйти**. Войдите `viewer / Viewer#2026`.
2. У зрителя нет кнопок добавления и удаления, нет разделов «Зрители», «Пользователи». Откройте **Моя карта** — видна только своя карта KT-100037.
3. Введите в адресной строке `https://1kotleta1.github.io/YP/admin/users` — откроется экран «Доступ запрещён».
4. Выйдите и попробуйте войти `blocked / Blocked#2026` — «Учётная запись заблокирована».

**Главное — в SQL Editor** (это доказывает, что права проверяет база, а не кнопки в приложении). Вставьте и нажмите **Run**:

```sql
-- Запрос от имени зрителя viewer
select set_config('request.jwt.claims', json_build_object('sub', u.id, 'role', 'authenticated')::text, true)
  from auth.users u where u.email = 'viewer@kinoteka.test';
select set_config('role', 'authenticated', true);

select (select count(*) from movies_view) as movies,
       (select count(*) from viewers_view) as viewers_visible,
       (select count(*) from profiles) as profiles_visible,
       my_card()->'viewer'->>'card_number' as my_card,
       has_perm('catalog.edit') as can_edit_catalog;
```
Результат: `42 | 1 | 1 | KT-100037 | false` — зритель видит весь каталог, но из 14 зрителей только себя.

Затем замените запрос и нажмите **Run** (Supabase спросит про «destructive operation» — нажмите **Run query**, удаления не произойдёт):

```sql
-- Менеджер пытается удалить жанр навсегда
select set_config('request.jwt.claims', json_build_object('sub', u.id, 'role', 'authenticated')::text, true)
  from auth.users u where u.email = 'manager@kinoteka.test';
select set_config('role', 'authenticated', true);

delete from genres where id = 1;
```
Результат: `ERROR: PT403: Недостаточно прав: «удаление навсегда» не разрешено роли «менеджер».`

Скажите: «даже если обойти приложение и отправить запрос напрямую, база не даст сделать то, что роли не разрешено».

Правила можно показать в **Authentication → Policies** (или **Database → Policies**): у каждой таблицы правила `read`, `write`, `change`, `remove`.

## Возможные вопросы и ответы

**Где у вас сервер?**
Серверная часть — проект Supabase: база PostgreSQL, REST API (PostgREST) и сервис входа (Supabase Auth). Своего кода сервера нет, вся логика — в `schema.sql`: функции, триггеры и правила RLS.

**Чем это отличается от ПР6?**
В ПР6 был свой сервер на Node.js, данные жили в памяти и сбрасывались при перезапуске. Теперь данные в настоящей базе и сохраняются, а права проверяет сама база.

**Ключ API лежит прямо в коде сайта — это не опасно?**
Это публикуемый (publishable) ключ, он и должен быть виден. Доступ ограничивают правила RLS. Секретный ключ (`sb_secret_…`) в приложение и в репозиторий не попадает.

**Что такое RLS?**
Row Level Security — правила на уровне строк. Для каждой таблицы задано, какие строки может читать и менять пользователь. Например, зритель видит только свою строку в `viewers`.

**Как база узнаёт роль пользователя? Нельзя ли подменить роль в браузере?**
Нельзя. Роль берётся из таблицы `profiles` по идентификатору пользователя из подписанного токена (`auth.uid()`). Подпись проверяет Supabase. Роль в браузере влияет только на то, какие кнопки показаны.

**Где хранятся пароли?**
В Supabase Auth (`auth.users`) в виде хеша bcrypt. В таблицах приложения паролей нет.

**Как развернуть базу заново?**
Создать проект Supabase, выключить Confirm email, в SQL Editor выполнить `schema.sql`, затем `seed.sql`, записать адрес и публикуемый ключ в `env/supabase.json`.

**Как работают коды ошибок?**
Функция или триггер поднимает ошибку с кодом `PT403`, `PT409` или `PT422` — PostgREST превращает его в HTTP-ответ с таким же кодом. У 422 в поле `details` лежат ошибки по полям, приложение показывает их под полями формы.

**Почему Supabase, а не PocketBase?**
Supabase — это настоящий PostgreSQL: связи, транзакции, триггеры и правила RLS пишутся на SQL, а REST API и вход платформа даёт готовыми. Бесплатного тарифа хватает, ничего не нужно запускать на своём компьютере.

## Если что-то пошло не так

| Что случилось | Что делать |

| Сайт пишет «Не удалось соединиться с сервером» | база уснула: Supabase → проект kinoteka → **Restore project**, подождать 1–2 минуты, обновить страницу |
| Выкинуло на экран входа | выход по неактивности через 3 минуты — войти снова |
| После показа нужно вернуть данные в начальное состояние | SQL Editor → выполнить `Итоговая/supabase/seed.sql`. Пользователи, зарегистрированные на защите, после этого перестанут входить — удалите их в **Authentication → Users** |
| Белый экран на сайте | обновить страницу с Ctrl+F5; проверить, что последний запуск в Actions зелёный |

Подробно всё описано в отчёте `Итоговая/Отчет Итоговая.docx`.
